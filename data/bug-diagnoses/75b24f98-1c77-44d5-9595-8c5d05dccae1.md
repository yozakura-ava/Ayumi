## Triage

Two close-path fidelity defects in the blend backtest harness surface from the
2026-09-08 blend-level WF re-run (KZ fix restored after card f30917a6). With KZ
back online, the harness now exercises 6 strategies (per dispatch note from
Craig, 2026-09-08 14:07 EDT). After Bug 1 (aa3a1cbe) and Bug 3 (047cd91d) are
landed, the only remaining source of P&L bias on the harness XAUUSD path is the
close-path fidelity:

1. **SL fills past level** — SL closes use bid (LONG) / ask (SHORT) as the fill
   price; for a 4.5-pip stop the bar's excursion lands the fill 50–275 pips
   past the level, producing 2.27× P&L bias on SL closes. The bar-low in
   XAUUSD routinely overshoots tight stops; using the bar's tick as the fill
   price is an optimistic bias on the LOSING side (it overstates losses).
2. **Pre-trade FTMO ordering** — `FTMOGuard.update()` only fires AFTER
   `_evaluate_strategies(symbol)` accepts an order. A same-bar entry that
   breaches the 3% daily-DD line is accepted first, then frozen, but the
   damage is already realized inside that bar. The guard must gate entry
   BEFORE the order is routed.

Both defects live in code paths the parent diagnosis could not pin precisely due
to the original 30-exec-call/turn cap. This diagnosis traces each defect to a
specific file/line and proposes a surgical fix within the 4-file lane cap.

## Reproduction

```python

from core.types import Position, TradeDirection

om = OrderManager()

    position_id="test",
    symbol="XAUUSD",
    direction=TradeDirection.LONG,
    entry_price=3360.00,

# Fix: pos.closed_price == 3350.37 (the SL level)

```

## Root Cause

### Bug A — SL fill past level (close-path defect)

**File:** `src/forex_bot/adapters/ctrader/order_manager.py`
**Lines:** 578–591 (function `update_position`)

```python
if self._check_stop_loss_hit(position, current_price, bid, ask):
    sl_fill = bid if position.direction == TradeDirection.LONG else ask
    self._close_position(
        position,
        sl_fill if sl_fill > 0 else position.stop_loss,
        reason="sl_hit",
        contract_size=effective_contract_size,
    )
```

`_check_stop_loss_hit()` returns `True` when the bar's bid (LONG) or ask
(SHORT) touches/passes `position.stop_loss`. The close then passes that
same bid/ask as `exit_price`, so the fill lands wherever the bar excursion
ended — typically dozens of pips past the configured level for tight
XAUUSD stops. For a LONG with SL=3350.37 and bar-low bid=3347.62 the fill
is 2.75 price units past the level (≈ 27.5 pips on the 0.1 pip convention;
275 pips on the 0.01 pip convention used in the harness log's strategy
report). Symmetric for SHORT.

This is the "close path" the parent diagnosis called out as Bug 2
("only 1 of 6 close") — once a fill-driven position diverges, the order
manager runs it at the wrong price, the cumulative P&L accumulates
the bias across many small SL hits, and the harness's only-1-closes
sample understates the bias because the other 5 positions never close
under the harness's rush-to-final-state logic.

### Bug B — Pre-trade FTMO ordering (eval-loop defect)

**File:** `scripts/backtest_blend_harness.py`
**Lines:** 935–982 (eval loop)

The harness already calls `_ftmo_guard.update(balance, open_n)` AFTER every
`_evaluate_strategies(symbol)` (card aa3a1cbe landed that). But:
- `update()` only RECORDS state and FREEZE/KILLs a breach that has
  already been realized.
- It does NOT gate entry.
- Inside `_evaluate_strategies`, the engine calls `_route_signal` →
  `blend_runner.on_signal` → orchestrator accepts → order_manager opens.

So a same-bar entry that would push daily-DD to 3% is accepted first,
_then_ the guard fires. The fix is to call
`_ftmo_guard.should_allow_new_position()` BEFORE
`_evaluate_strategies(symbol)` and skip routing when blocked. The
post-eval `update()` stays — it's still needed for the detection +
FREEZE/KILL side-effect (mirrors production pattern in
`scripts/launch_blend_forward_test.py:1984-2010`).

## Fix Strategy

### Bug A fix
**Scope (1 file):** `src/forex_bot/adapters/ctrader/order_manager.py`

Change `update_position()` SL branch to fill AT `position.stop_loss` level,
not at the bar's bid/ask excursion:

```python
if self._check_stop_loss_hit(position, current_price, bid, ask):
    # Card 75b24f98: SL fills at the configured SL level, NOT at the
    # bar's bid/ask excursion. The previous code used ``bid``/``ask``
    # past the level by the bar's excursion → 50–275 pip past-tight
    # stops on XAUUSD (≈2.27× P&L bias on SL closes).
    # Conservative pips-per-side slippage model is a SEPARATE concern
    # (card 46b631ab) and not duplicated here.
    self._close_position(
        position,
        position.stop_loss,
        reason="sl_hit",
        contract_size=effective_contract_size,
    )
```

TP branch UNCHANGED (not in scope; TP can be a follow-up).

**Side effects:** Production also benefits (the close-path is shared
between paper trader / live via the same `update_position` entry). Net
effect on live: SL exits become more conservative (better fills — they
fill AT the configured level, not wherever the bar ran to). This is the
canonical FTMO-style fill model.

**Test plan:** Synthetic `Position(LONG, entry=3360, sl=3350.37)` +
`update_position(current=3349, bid=3347.62)`:
- Before fix: `closed_price == 3347.62`, `closed_pnl` overstates loss.
- After fix: `closed_price == 3350.37` (SL level), P&L == (3350.37−3360)·0.10·100 = −$96.30.

Symmetric test for SHORT.

### Bug B fix
**Scope (1 file):** `scripts/backtest_blend_harness.py`

In `run_backtest()`, inside the per-bar eval loop, add a pre-trade
`should_allow_new_position()` gate BEFORE the
`engine._evaluate_strategies(symbol)` call:

```python
# Card 75b24f98: pre-trade FTMO gate (guards same-bar entries that
# would breach daily-DD). Post-trade _ftmo_guard.update() is kept for
# detection (mirrors production main loop pattern).
can_open, gate_reason = _ftmo_guard.should_allow_new_position()
if not can_open:
    if ftmo_blocked_counter.setdefault(key, 0) < 3:
        logger.info("FTMO pre-trade gate blocked: %s", gate_reason)
    ftmo_blocked_counter[key] = ftmo_blocked_counter.get(key, 0) + 1
else:
    engine._bar_completed[key] = True
    engine._evaluate_strategies(symbol)
    engine._bar_completed[key] = False

# Post-trade update (existing aa3a1cbe pattern, unchanged)
open_n = len(paper_trader._order_manager._positions)
_ftmo_action = _ftmo_guard.update(paper_trader._current_balance, open_n)
...
```

**Side effects:** None — pre-trade gate is informational on already-FREEZE
states (no-op for ALLOW). Reduces same-bar breaches, then post-eval
update() records the breach and halts the loop if it escalates.

**Test plan:** Source-level invariants (gate present, called BEFORE
`_evaluate_strategies`, called AFTER `_ftmo_guard.update` not before
it). Behavioral: FTMOGuard in FREEZE → pre-trade gate returns False →
no entries accepted in the eval loop.
