## What
Resolve a blend-accepted order's canonical `signal_id` when the execution callback supplies a synthetic/default identity, record the position in any available paper order manager, and preserve the resolved mapping for the SL/TP close callback.

## Why
PaperTrader already creates a Position for a paper fill, but the blend runner's `register_position_mapping` path records a different default timestamp identity. The resulting `KeyError` in `BlendForwardTestRunner.on_fill` leaves the sizer risk reserved, so subsequent accepted orders cannot execute. A defensive unresolved-ID queue and optional order-manager mirror make the mapping explicit without relying on caller identity construction.

## Implementation Plan
1. Track accepted, not-yet-mapped canonical signal IDs in registration order.
2. In `register_position_mapping`, accept a canonical ID directly or resolve the oldest still-open accepted ID when the caller supplies a synthetic/default ID.
3. If a paper trader/order manager is available through the runner or the caller's optional argument, preserve an existing Position or mirror the accepted order with symbol, direction, volume, entry, SL, and TP fields.
4. Add a regression test for an accepted blend order, unresolved execution identity, SL-triggered paper update, PnL, and released sizer risk.

## Edge cases
- No paper trader/order manager is available: mapping must still resolve the canonical ID.
- Multiple accepted orders with one paper fill: resolve the oldest open canonical ID and do not map a rejected/cancelled one.
- Reusing a signal ID after close: clear queue/mapping state and permit a fresh registration.
- SL direction reversal: preserve the orchestrator's direction and use the paper position's existing direction semantics.
